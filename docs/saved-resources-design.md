## Proposed data contract

A dedicated `saved_resource` association refers to the **existing caregiver primary key** and a qualified public resource ID. Reuse the existing person/profile identity; do not create another profile, passport record, partner record or caregiver. No copied title, URL, message, health information or loved-one data in the association. Proposed columns: caregiver_id, resource_id, created_at; composite unique key (caregiver_id, resource_id). Proposed catalog foreign key or equivalent transactional published-ID validation must be resolved against actual storage before migration review. No migration number reserved and no SQL included/applied here.

Resource IDs: proposed lowercase ASCII opaque slug, 1–80 characters, anchored `[a-z0-9][a-z0-9_-]{0,79}`. Server resolves only a currently published, saveable catalog entry. Reject unknown/retired/placeholder IDs; never accept a client URL, owner ID or title. Catalog and association race behavior must be tested: concurrent retirement must not create a new active association. Reads return public resolved metadata only after validating the caller's own associations; retired items appear as unavailable with Remove, never an arbitrary obsolete destination.

## Save and My Resources behavior

Proposed Save button beside eligible cards, with keyboard-visible state and an accessible result region. Anonymous users are asked to sign in through the normal portal flow; no association is written from an unverified form, query email or browser cache. Do not send a sign-in email automatically from a public Save click. A resource-only return destination must be allowlisted and must not encode contact details or an arbitrary redirect. After sign-in, require an explicit Save confirmation; never replay a stale browser intent silently.

Signed-in Save becomes Saved only after an authoritative successful receipt. Disable duplicate clicks while pending; errors preserve a retry option without claiming success. My Resources lists only the signed-in owner's saved items, newest first with a stable tie-breaker, empty state, resource link and Remove. Removing a bookmark never deletes the public resource. Do not hide the public library or turn public content into authenticated-only content. Proposed maximum 200 saves per owner and pages of at most 50 require product/operating review; they are bounds for the future candidate, not existing policy.

Proposed routes: GET own saved list with a bounded opaque cursor; PUT one association; DELETE one association. No owner in path/query/body. PUT and DELETE are naturally idempotent under the composite unique key: repeated Save returns the same association/creation time; repeated Remove succeeds without another effect. Strict method/path/JSON-key checks, bounded body (proposed 1 KiB), typed resource_id only, no bulk mutation. Scope any additional operation receipt key to verified owner + action + resource ID; changed payload under a reused key conflicts. Use atomic constraints and affected-count/receipt checks, not read-then-insert optimism. A timeout with unknown commit status is reconciled by reading this owner's association; never synthesize a success or replay unrelated operations.

## Authentication, ownership and preview

Reuse the verified portal cookie/session mechanism in `functions/api/portal/[[path]].js`, checking expiry, current nonarchived caregiver and revocation before every read/write. Audit the actual cookie parser, not just its name; duplicate/malformed cookies must fail closed. Identity is server context only, never supplied actor/email/owner JSON. Mutations require strict same-origin Origin, Fetch Metadata and existing portal CSRF proof; GET is read-only and private/no-store. Permission must be rechecked within the transaction or equivalent revocation witness, not merely before a delayed write. No shared cache of private lists. Test missing/expired/revoked session, duplicate cookies, off-origin/missing CSRF, foreign IDs/cursors, archived caregiver, schema absence, retirement races and concurrent duplicate Save/Remove.

Preview must preserve the current preview recipient/QA namespace restrictions; a production identity does not automatically grant staging access. No copying production bookmarks into preview. Synthetic examples use fictional caregiver IDs and catalog fixtures only. Staff does not inherit a read-all bookmark list: the feature is owner-only. Any later Staff assistance/export access needs an explicit separately reviewed permission and purpose, current active Staff authorization and minimal audited projection. Existing QA sample cards remain labeled and must never be presented as saved rows.

## Privacy and lifecycle dependencies

Bookmarks can reveal interests even when their targets are public. Keep them out of analytics, notification email, generic notes, assistant prompts, public URLs and unrelated Staff searches. Proposed audit metadata is actor/action/resource ID/time and outcome, without duplicating public content or personal fields; audit access/retention must be approved. No email or notification is needed for saving.

Proposed active Remove physically removes the active association; audit and backup copies are separate. Account archival immediately revokes access; actual account deletion cleanup, retention duration, correction channel, audit redaction and handling of removed catalog entries require operating policy. Do not invent a purge period or silently inherit respite retention. Export only the authenticated owner's association IDs/timestamps plus resolved public titles if useful; qualify approved owner export authentication and delivery rather than placing private exports in public storage. No arbitrary owner export endpoint.

Existing `workers/backup` and `scripts/restore-from-backup.mjs` are dependencies, not proof that new private rows are safe. Before collection: enumerate actual table inclusion, D1/R2 readers, storage/encryption/access, export destinations, backup expiry and restore procedures. Test removal reconciliation so restoring an old backup cannot resurrect a removed bookmark: approve and implement either a bounded deletion ledger/replay mechanism or an equally explicit restore reconciliation design before release. Ledger scope, retention and authorization remain unresolved; this artifact does not claim active deletion erases historical backups. Use synthetic restore fixtures, never a private dump to demonstrate this.
