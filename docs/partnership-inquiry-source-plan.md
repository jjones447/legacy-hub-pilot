# Partnership inquiry: synthetic preview and proposed live source

This candidate delivers a local demonstration, not a real inquiry service. Customer scope is the seven Get Involved interests and name, optional organization, email, optional phone, interest, and message. Staff dashboard plus email is requested if possible. The confirmed recipient is held in the private request ledger and must be configurable; no real recipient or provider key is embedded in source/fixtures.

## Delivered preview

`node scripts/build-partnership-preview.mjs /tmp/<new-empty-directory>` produces only four static files. Deploy that separate package to a preview branch. The ordinary production allowlist excludes docs/previews and this candidate changes no existing navigation, inquiry destination or production page. The page prominently says fictional details only, nothing is sent/saved. Example uses example.invalid. Local feedback clears values and never echoes personal input or implies provider acceptance. No API, fetch, storage, analytics or email. CSP blocks connections and form submission. Controls start disabled; there is no HTML form or submit button. URL ?interest=event-respite can preselect ONLY a known interest; other query values cannot populate contact fields. Production Event Respite links stay unchanged until a REAL approved/qualified service exists.

## Proposed dedicated entity/handler (NOT implemented or applied)

Use a dedicated `partnership_inquiry` entity. Do not call generic /api/intake, upsert caregivers, infer membership, enrol anyone, match on a caregiver email, or put partner details into caregiver records. Proposed bounded columns: id; unique request key; payload digest; name; optional organization; email; optional phone; allowlisted interest; message; status(new/in_review/closed); revision; created/updated times. A future candidate migration must specify exact checks/indexes and reconcile the then-installed catalog; no number is reserved here. Avoid sensitive submitted details in generic notes, audit payloads, URLs, metrics or AI prompts.

Proposed handler: dedicated POST endpoint with exact Origin/same-origin defense, bounded JSON streaming and strict typed allowlist; required name/email/interest/message; optional organization/phone. Limits: name120, organization200, email254, phone40, message2000; trim text, reject controls/unknown keys and invalid email/phone/interest. An unchanged client-generated opaque idempotency key retries the SAME request; changed payload under the same key is a conflict. Atomic inquiry receipt + audit; verify affected counts. No success claim from an unknown/incomplete DB outcome and no blind replay.

Before public collection, qualify abuse controls: IP and global quotas, payload bounds and provider-independent throttling without revealing other inquiries. Source policy/rate choices need review and operating-owner acceptance, not a fabricated production quota. No CAPTCHA provider/account assumed or added in this preview.

## Staff access and personal information

Dedicated Staff queue/detail/status mutation under existing verified Access identity and current ACTIVE Staff lookup on every request, with bounded results, owner-appropriate permissions and revision checks. Public responses contain only the submitter's opaque receipt; no public enumeration/search/detail endpoint. Private projection must recheck current authorization at projection/write, including mid-request revocation witnesses. Admin role is not inferred from email spelling or a name.

Staff operational access, retention duration, correction/removal contact and process, deletion/redaction semantics, export permissions and audit minimums must be agreed before live collection. No retention policy is invented here. Existing backup/export jobs enumerate tables; a new table is NOT an isolation boundary. Qualify actual D1/R2 readers, export destinations, expiry/access, restore procedures and removal reconciliation. No private dumps, new Staff grants or live records are needed for this synthetic preview.

## Notification design and gaps

Dashboard receipt is the primary durable submission outcome. Email is a separate optional notification, never a prerequisite for saving an accepted inquiry and never a success guarantee from HTTP alone. Keep recipient configurable through the approved deployment configuration workflow; the private ledger contains the confirmed temporary recipient. Do not allow public requests to choose recipient/subject/HTML. Use minimal content (opaque inquiry reference + authenticated Staff link) rather than copying the message/contact into email by default; operational owner must approve the actual envelope/content.

Proposed outbox row keyed uniquely to inquiry + notification kind. Track pending, sending, accepted, failed and outcome_unknown with attempts/provider reference. Worker claims with CAS/lease and uses provider idempotency only if actually supported/qualified. Never equate provider acceptance with human delivery. A timeout after possible provider acceptance stays unknown until reconciliation; automatic retries must not duplicate unknown sends. Retry only confirmed pre-send/definitive failures under bounded policy; Staff sees notification state without changing the durable inquiry receipt. Sending/provider credentials, recipient verification, retry/retention policy and real provider behavior are NOT qualified by this plan. If email cannot be authorized, dashboard-only fallback must be communicated by the conversation owner rather than silently promised as both.

## Ordered gates and candid state

Delivered: isolated working static demo, tests and this source plan. Not built: real handler/entity/migration, Staff queue/projection, outbox/sender and operational evidence. New D1 writes need the existing exact staging target/additive-migration authorization, reviewed source and backup/restore readiness. Production schema/collection and real email have their own existing Jacob/requester/authority gates; custody or the confirmed address does not grant them. Requester tries this synthetic preview first; independent exact-head review and requester approval do not themselves activate collection. No live date is promised. The existing Get Involved contact fallback remains until a real qualified form is published.
