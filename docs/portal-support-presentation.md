# Portal and Request Support presentation candidate

This artifact implements the requested presentation in an isolated static preview, not in the installed portal. Production HTML, app.js, Functions, records, scoring and integrations are unchanged. No form submits, API requests, persistence, email or sign-in occurs. The Send My Request button is disabled. Examples are fictional and hidden until explicitly enabled; clearing them removes their display. Deploy only the five-file preview package, never as the production site.

The layout preserves the four requested actions, compact profile, wellness explanation/history disclosure, resource link and empty updates. Grant and Memory Social displays are absent from this candidate; underlying records remain untouched. No saved-resource feature, profile editor or functional check-in is claimed. The existing real portal remains the place for those supported actions. The five needs are selectable for layout review only. Phone call/Text/Email are presentation choices, not supported notification promises.

## Source integration gaps

- app.js submitSupport directly dereferences supWho, accepts one supWhat value and posts to public /api/intake. Removing the production field independently would break submission. A coordinated frontend successor must remove that dependency and preserve validation and error behavior.
- functions/api/intake.js and _shared.mjs do not establish a verified portal caregiver association for this request. Reuse the existing verified session/current nonarchived caregiver and same-origin/CSRF boundary for any future owner route; never trust an email or actor supplied by the browser. No such route is implemented here.
- The intake writer does not persist structured multi-select needs or preferred_contact. caregiver.preferred_contact existing in schema is not evidence that Text is supported. Typed payload, migration/storage decision, idempotency, retry/outcome handling and Staff projection need reviewed implementation before enabling submission.
- Existing followup open/done/dismissed and the separate gated #362 status vocabulary do not establish Received/In Review/Followed Up/Closed. Do not invent a status from these fields. Actual Staff workflow and owner-visible transitions require qualification.
- /api/portal/me currently includes grant records and a server QA-sample option. A future production presentation successor must remove grant/social rendering without deleting records and replace automatic sample mixing with explicit opt-in. This static preview does not change that response or its renderer.
- Wellness must reuse /api/portal/wellness owner/session checks, real scores/date/history and unchanged scoring; no interpretation of a score as safety, diagnosis or good/bad. The displayed example is fictional. Resource favorites and profile editing remain separate gated work.

Proposed mapping to #377 seven-need taxonomy, requiring owner confirmation before a writer: break → respite; caring help → behaviors/education clarification; connect → social; resources → education/other resources clarification; unsure → unclassified/Staff clarification. Stress and wellness remain available in later clarification rather than inferred or silently discarded. Multiple selections must remain distinct, not be flattened into an ambiguous message.

The requested two-business-day follow-up wording is shown for copy review; operating Staff capacity and response ownership are not verified by this preview. No service-level guarantee is established. Existing support/crisis destination is secondary. No production-content-store read or write was performed: published overrides, installed presentation and authenticated runtime behavior remain unverified for this candidate. #371's qualified Staff content publisher remains unavailable on this seat; do not substitute raw D1 writes or acquire credentials.

## Validation and release boundary

Build with `node scripts/build-portal-support-preview.mjs /outside/empty-directory`. CSP denies connections and form actions; package contains no Functions or configuration. Tests check opt-in example clearing, no persistence/network primitives, disabled submission, exact key copy and multi-select controls. Source responsive rules use one column below 650px and 44px controls. Browser pixels, keyboard/screen-reader behavior, actual mobile overflow and authenticated integration have not been exercised here. Independent exact-head review and requester layout approval are required; neither authorizes backend/storage activation or production publication. A production implementation needs a separate coordinated, reviewed source candidate and the existing authority gates.
